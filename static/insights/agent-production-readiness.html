Why AI agents stall between pilot and production, and the eight things production needs

Monovus · 4 November 2026 · about 7 minutes

Most AI agent pilots succeed at the thing they were built to show. The agent answers the question, files the ticket, drafts the reply. Then the project stops. The demo didn't fail. Production asks different questions, and the pilot was never built to answer them.

Gartner expects over 40% of agentic AI projects to be cancelled by the end of 2027, because of escalating costs, unclear business value or inadequate risk controls (Gartner, 25 June 2025). None of the three is about the model. Each is a question a leader asks before putting the company's name on something: what will it cost, what is it worth, and what happens when it goes wrong?

This article is for the person who has to answer those questions, and for the technical lead who has to give them the evidence.

The demo answers one question. Production asks three.

A demo proves capability: the agent can do the task, on a good day, with its builder watching. Production needs the same agent to be affordable at volume, accountable for results and safe when nobody is watching. Those are properties of the system around the model, and most pilots don't have that system yet.

That is why the stall is common, and why it feels sudden. The pilot team did good work, but the work that remains is different in kind: less prompt-writing, more measurement, permissions and process. It often has no owner, because it falls between the team that built the agent and the teams that run production systems.

The gap shows up in the returns. In a Gartner survey published on 4 November 2026, just 4% of customer service organizations had achieved the ROI they expected from their AI initiatives (Gartner, 4 November 2026).

The eight things production needs

We judge whether an agent is ready on eight dimensions. One covers business value; seven are controls. They are the same eight our free assessment scores, and each is described here in business terms first.

A clear owner and a measurable payoff

An agent without an owner has no one to defend it at budget time. Before anything technical, production needs one accountable person and one number the agent must move, such as hours saved a week or tickets resolved without a person, measured against today's baseline. If that number can't be named, the pilot isn't ready, however well it demos.

Quality you can measure

Every prompt edit, model upgrade or new tool can make answers worse. The control is a set of real cases with known good answers, run before every change, where a lower score blocks the release. Start with 25 cases taken from real transcripts. It is the cheapest way to stop learning about regressions from customers.

Every decision visible

When a customer complains, your team should be able to see what the agent did: which model calls it made, which tools it used and which documents it retrieved. Without that trace, a fixable bug turns into an argument. With it, most incidents can be explained quickly. Add one alarm on the error rate, so failures reach you before complaints do.

Predictable cost

Inference cost grows with usage, and agents can loop. Production needs cost measured per task, a monthly budget with alarms at 50%, 80% and 100%, and limits per user or per task. Routing simple turns to a smaller model is one of the first savings to look at.

The agent can only do what it should

A prompt is a request, not a control. If the agent can change anything in your systems, the rules about what it may do have to live outside the prompt, in a policy layer checked on every tool call, with permissions that allow nothing more. On AWS, AgentCore Policy works with AgentCore Gateway to intercept every tool call before it runs.

Access you can account for

When the agent acts in another system, you need to be able to say whose identity it used. A shared admin key fails that test and multiplies the damage of a leak. The agent should act as the signed-in user, or as its own named identity with scoped permissions, and every key should sit in a secrets manager with rotation on.

A fast way back

Bad changes happen. What matters is how long they stay live. Put prompts, tool definitions and settings in version control, and rehearse one rollback before launch, so the last good version is minutes away and nobody has to work out what changed while customers wait.

Ready for incidents and audits

Launches stall in security review when the evidence is scattered, and incidents stall when the one person who understands the agent is away. A one-page runbook (symptoms, owner, how to pause the agent, how to roll back) and an evidence pack kept current solve both.

What this means for the launch decision

Score the agent honestly on all eight before setting a date. A low score is not a failure; it is a list. Most gaps close in weeks rather than quarters, because the parts already exist. On AWS, Amazon Bedrock AgentCore provides runtime, gateway, policy, identity, memory, observability and evaluation services that cover most of the seven controls. The work is configuring them for one agent, proving they work, and handing them to the team that will run it.

Two warnings. First, a good score is not permanent: models, prompts and usage change, so evaluations and cost reviews have to keep running after launch. Second, if the honest answer is that the agent should not go to production yet, a narrower agent that does one task well is often a better outcome than a broad one nobody trusts.

Where to start

If you lead the business, ask for the eight answers in writing. If you lead engineering, start with the test set and tracing: every other control is easier to prove once you can measure quality and see what the agent did.
